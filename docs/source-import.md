# Source import policy

[← Kairo68](../README.md)

This repository is independent. Its only Git remote is `origin`, pointing to this project's repository. The first-party Kairo frontend is pinned at `shared/` as a submodule. Do not add an `upstream` remote, fork relationship, other submodule, subtree sync, or automated upstream merge. Third-party source is copied in as pinned snapshots under `third_party/`.

## MAME snapshot

`third_party/mame/` holds the part of MAME 0.289 that the X68000 driver needs.

[`shared/tools/import_mame.py`](../shared/tools/import_mame.py), with what is Kairo68's own in [`tools/mame_import.py`](../tools/mame_import.py), chose the files from the extracted archive:

1. MAME's own `scripts/build/makedep.py sourcesproject` (the logic behind `make SOURCES=...`) lists the driver's sources and the CPU, sound, machine, video, bus and format options it uses.
2. Those options are resolved to files through MAME's `scripts/src/*.lua` file lists, and the always-present shared floppy format code is added.
3. `src/emu`, `src/lib/util` and the top level of `src/osd` are copied whole.
4. The set is closed over `#include`: each included header is added, along with the source file next to any device, driver or format header, until nothing new is reached. Generated layout and font inputs are added from their source files.
5. Every 3rdparty library that a selected file includes, plus the libraries the core always links (expat, zlib, lzma, zstd, utf8proc, flac, softfloat3, rapidjson, asio, and pugixml, libjpeg, nanosvg and aes256cbc, which MAME includes through their own include directories), is copied whole so its license files stay with it.
6. MAME's `COPYING`, `README.md` and `docs/legal/` are copied.

The import produced 6,294 files (6,253 without the nested Git metadata below): the 5,928 of the first import (2026-10-21) and, added 2026-10-22: the OSD platform services the core runs on (`src/osd/modules/file/` for POSIX and Windows files, directories, ptty and sockets, `src/osd/modules/lib/osdlib_unix.cpp` and `osdlib_win32.cpp`, the Windows helpers `src/osd/windows/winutil.*` and `winutf8.*` for the host test, and `src/osd/interface/audio.cpp`, `inputseq.cpp` and `nethandler.cpp`); the four include-directory libraries above; the devices MAME's device scripts list outside any option block (NVRAM, RAM, floppy drives, volume filters and the like at the top of `machine.lua`, `sound.lua` and `video.lua`); and the files of option blocks written as `opt_tool(CPUS, "...")` or guarded by a local set from one (the CPU disassemblers). Kairo68 supplies its own video, sound and input in place of MAME's OSD modules. `third_party/mame/KAIRO_IMPORT.txt` records the driver, the 3rdparty libraries, and the full `makedep.py` output. To repeat the import, run `tools/import_mame.py <extracted-mame-root> <new-destination> src/mame/sharp/x68k.cpp` and compare with the committed tree.

The importer leaves out nested Git metadata (`.gitignore`, `.gitattributes`, `.gitmodules`, `.github/`), so that every copied file is tracked. One symbolic link in zstd's CLI tests (`tests/cli-tests/bin/unzstd`) could not be created on Windows and is absent. The pre-generated 68000 decoder sources (`src/devices/cpu/m68000/m68000-*.cpp`) are part of MAME's tree and are kept as shipped.

## Local changes

`shared/tools/import_mame.py` applies Kairo68's changes to the copied sources from `tools/patches.py` with `shared/tools/local_patches.py`; each replaces text that must occur exactly once, so an import against a MAME that moved the code stops instead of patching the wrong place.

MAME does not mark the x68000 driver as supporting save states. These changes make a loaded state restore the machine exactly; `core/test/boot_test.cpp` checks it by comparing every saved entry, frame by frame, for a second after a save and after a load.

- `x68k-save-state` (`src/mame/sharp/x68k.cpp`, `x68k.h`, `x68k_v.cpp`): the driver registered only its text and graphics VRAM and sprite registers. A loaded state kept the video controller, system port, I/O controller, ADPCM, PPI and FDC control state, SRAM, and the PCG and BG RAM from before the load, so the picture could stay black or show wrong patterns. The change registers that state and, after a load, reconnects the FDC to the selected drive, redecodes the PCG patterns and redraws both BG layers.
- `upd765-save-state` (`src/devices/machine/upd765.cpp`, `upd765.h`): the uPD765 family's live read/write state is not saved (MAME has those registrations commented out), nor is the data separator PLL inside it or the drive it reads. A read in progress at the save continued after the load from the state of before the load, lost its sector, and the X68000 saw End of Cylinder. The change saves both live states, their PLLs and drives.
- `floppy-save-state` (`src/devices/imagedev/floppy.cpp`): the drive saves its flux cache but not where the cache's weak zone starts or whether the track has unwritten changes.
- `rtc-save-state` (`src/emu/dirtc.h`, `dirtc.cpp`, `src/devices/machine/rp5c15.cpp`): `device_rtc_interface` counts the date and time in registers no state held, so after a load the clock ticked on from the time before it; the RP5C15 also left out its RAM.
- `hd63450-save-state` (`src/devices/machine/hd63450.cpp`): the DMA controller leaves out its latched bus-error code and its DTACK line.

- `osdlib-without-sdl` (`src/osd/modules/lib/osdlib_unix.cpp`): the POSIX OSD library reaches the clipboard through SDL, which only MAME's SDL OSD links. Kairo68 supplies its own OSD and has no SDL, so without `OSD_SDL` the file uses the clipboard stubs MAME already has for Android.

MAME's x68000 SASI hard disk controller was not usable for booting:

- `x68k-sasi-count` (`src/mame/sharp/x68k.cpp`, `x68k.h`): the IPL boots from SASI only when SRAM byte 0x5a counts the connected drives, which the owner sets with SWITCH.X; MAME's SRAM starts blank. The driver reports the attached drive in that byte, as it already reports the configured RAM size at 0x08.
- `x68k-sasi-dma` (`src/mame/sharp/x68k_hdc.cpp`, `x68k_hdc.h`, `x68k.cpp`): the IPL and Human68k move SASI data through DMA channel 1 on the controller's REQ line, which MAME never connected, so the first read never finished. The controller drives DRQ from REQ during its data phases, connected to the HD63450's DRQ1, and requests the first byte of a read or write after the average rotational latency of a 3600 rpm disk (1/120 s) rather than 450 ns: the HD63450 takes the request on its edge, and a request made before the IPL starts its DMA channel is never served.

Speed (Kairo68#5). Each change keeps the guest's behavior exactly: `tools/perf/verify-all.ps1` runs games before and after it with `core/test/game_profile` and every frame's picture and sound must match.

- `perf-counters` (`src/emu/schedule.cpp`, `sound.cpp`, `src/devices/cpu/m68000/m68000.cpp`, `src/mame/sharp/x68k_v.cpp`): a measurement build (`KAIRO68_PERF`, `core/kairo68_perf.h`) counts the 68000's instructions and timeslices, timer callbacks by timer, `screen_update` calls and lines, and their host time. Without `KAIRO68_PERF` the hooks are empty.
- `mfp-timer-elapse` (`src/devices/machine/mc68901.cpp`, `mc68901.h`): MAME's MC68901 fired a scheduler timer at every prescaled count, so a timer in delay mode cut the 68000's timeslices into a few hundred cycles. A delay-mode timer now fires only at the count where it elapses; a data register read, a control register write or a save computes the counter from the counts since then.
- `dma-drq-poll` (`src/devices/machine/hd63450.cpp`): an external-request channel's timer kept firing every bus clock (2 microseconds on the floppy channel) while DRQ was low, doing nothing but ending timeslices. It now stops at the first firing that finds DRQ low; DRQ's rising edge already restarts it.
- `x68k-deferred-partial` (`src/mame/sharp/x68k_crtc.cpp`, `x68k_crtc.h`, `x68k.cpp`, `x68k_v.cpp`): the CRTC drew each visible line at its hsync, about 460 `screen_update` calls a frame. The hsync now records the line the beam passed, and the lines waiting are drawn before anything the picture shows changes (video RAM, CRTC and video controller registers, palettes, sprites and BG, the system port, the raster copy), so each line is drawn from the state it had at its own hsync.
- `screen-color-getters` (`src/emu/screen.h`): reads back the screen's render colour and brightness. Kairo68 copies the finished picture from the screen's bitmap instead of rendering it (`core/x68k_machine.cpp`, `render_frame`) and applies the colour MAME's renderer would; the driver dims the screen from the monitor contrast for fades.
- `x68k-text-line` (`src/mame/sharp/x68k_v.cpp`, `x68k.h`): `screen_update` looked up the text layer pixel by pixel (`get_text_pixel`), rereading the scroll registers and four plane words for every pixel. Each line's text colours are now decoded once, reading each group of four plane words once per 16 pixels, with `get_text_pixel`'s expressions.
- `x68k-mix-hoist` (`src/mame/sharp/x68k_v.cpp`): `screen_update`'s mix reread the video registers, the bitmaps' bases and pitches and both palettes through their accessors for every pixel, and `get_gfx_pixel` re-derived the graphics layer's double scan and colour mode and divided for its row each time. These are now taken once per update or line, and the graphics pixel is decided by the same three branches on the same values, so every picture is unchanged (11 game runs, every frame's picture and sound matching). On the RG DS, Alien Syndrome at 25 MHz: 48.1 -> 57.3 frames a second (Kairo68#18).
- `m68000-idle-skip` (`src/devices/cpu/m68000/m68000.h`, `m68000.cpp`): the 68000 skips the passes of a busy-wait loop. `m_program` counts every write and every read at or above main RAM's end; when a pass of a loop starts at the same address as the last one within one `execute_run`, with nothing counted in between and the whole processor state (registers, prefetch and bus latches, pending interrupt, instruction state) the same, the cycles of the whole passes that still fit in the slice are used up at once and the rest runs normally. Nothing outside the CPU runs during `execute_run` (timers, DMA and interrupts act between slices), so the guest cannot tell. Kairo68 enables it with `enable_idle_skip` (`Config::idle_skip`); it refuses a CPU with an MMU or host callbacks, which act outside `m_program`. Alien Syndrome waited for each frame in `cmpi.b #2,($62b8).w; bcc.s` for 52% of its instructions; with the skip it runs 26,300 instead of 38,000 instructions a frame, every frame's picture and sound unchanged (11 game runs), and 56.97 -> 58.09 frames a second on the RG DS (Kairo68#12).
- `perf-fm-stage` (`src/devices/sound/ymfm_mame.h`, `src/emu/sound.cpp`): a measurement build counts host time in ymfm's synthesis (`fm_ns`) and the part of it inside the sound manager's end-of-frame update (`fm_tail_ns`), which a synthesis worker could not overlap with emulation (Kairo68#22). Alien Syndrome: 9.5% of the frame, 1.5% in the tail; Akumajou Dracula: 14.1%, 1.3%.
- `ymfm-synthesis-worker` (`src/devices/sound/ymfm_mame.h`, `ymopm.cpp`, `src/emu/sound.h`, `sound.cpp`, `3rdparty/ymfm/src/ymfm_fm.h`, `ymfm_opm.h`): the YM2151 synthesizes on a worker thread (`kairo/ordered_worker.h` from shared), in parallel with the emulation. The guest reads the chip's status, timers, IRQ and ports, which stay on the emulation thread with the device's chip; that chip stops generating and counts the clocks it would have (`advance_generated`: `engine_mode_write` starts timer B from them). A second chip on the worker is given the same calls in the same order (writes, deferred mode writes and interrupt checks, timer expiries, resets) in batches of 32 and generates each stream update's samples. A stream can leave its samples to be written later (`set_deferred_finish`, `put_at`); `do_update` has its sources write theirs before reading them, and `sync` before the buffer moves on. Saving waits for the worker and saves its chip; loading discards the worker's pending work. Kairo68 enables it (`Config::synthesis_worker`). Every frame's picture and sound match the original build (11 game runs) and a saved state loads back identically (`boot_test`). RG DS, same build with and without: Alien Syndrome 58.11 -> 62.01 frames a second, Akumajou Dracula 104.42 -> 115.15 (Kairo68#22).
- `resampler-inline-reader` (`src/emu/resampler.cpp`): the lofi resampler (`apply`, `apply_copy`, `apply_add`) reads its source samples through an inlined lambda instead of a `std::function`: the same reads and sums in the same order, without an indirect call per source sample on the emulation thread. Every frame unchanged (11 game runs); within measurement noise on its own, +0.45% on the RG DS (Kairo68#23).
- `m68000-direct-memory` (`src/devices/cpu/m68000/m68000.h`, `m68000.cpp`): the 68000 reads, writes and fetches plain memory through host pointers instead of the address space's dispatch. A 4 KB page is direct when every word of it is the same plain memory in order (checked with `get_read_ptr`/`get_write_ptr` when the page is first used); it is then read and written exactly as MAME's memory handler does (reads ignore the mask, writes apply it). Devices, unmapped space and ROM writes go through the space as before, and the pages are forgotten whenever the address map changes. Only a table load and a test are inline in the instruction handlers: inlining the whole lookup into thousands of them was slower than the dispatch. Kairo68 enables it (`Config::direct_memory`) except with `count_accesses`, whose taps on RAM it would go past. Every frame unchanged (11 game runs), saved states round-trip (`boot_test`); RG DS against the build before: Alien Syndrome 62.15 -> 62.47 frames a second, Aquales 81.36 -> 83.94 (Kairo68#13, #14).
- `mfp-usart-clock-replay` (`src/devices/machine/mc68901.h`, `mc68901.cpp`, `src/mame/sharp/x68k.cpp`): the MFP's timer B clocks the keyboard USART (`out_tbo_cb` to `tc_w`/`rc_w` only; the driver says so with `set_timer_b_usart_clock`), about 1,360 firings a frame and half of the 68000's timeslices. While the USART is idle (asynchronous mode, no loopback, the receiver's line marking with nothing in progress and no break, the transmitter not shifting with nothing to load and its output already at the level `tx_clock` sets, timer B's interrupt off), its clock edges only advance its own counters. Timer B then fires every 256 elapses, and the elapses between are replayed exactly as `timer_count` runs them (toggle TBO through the same callback, reload the counter, count from that elapse) before a register read, before a register write or a change on the serial input (which return timer B to firing at every elapse), and before a save (which saves it that way). Every frame unchanged (11 game runs, plus a run with key presses that change the game's sound), saved states round-trip; MFP firings 1,359 -> 9 a frame, 68000 timeslices 2,704 -> 1,359; RG DS: Alien Syndrome +8.3%, Aquales +8.9% (Kairo68#11).
- `x68k-gfx-hoist` (`src/mame/sharp/x68k_v.cpp`): `draw_gfx_scanline`'s 512x512 modes (16, 256 and 65,536 colours) take the special-priority test once a call and the destination, special-layer and GVRAM rows and the hbegin/hend bounds once a line, instead of every pixel rereading the video registers and computing its row addresses through `pix()`; each pixel takes the same steps on the same values. Every frame unchanged (11 game runs); RG DS: Alien Syndrome 64.90 -> 65.74 frames a second, every round ahead (Kairo68#18).
- `floppy-next-cell` (`src/devices/imagedev/floppy.cpp`): the floppy's flux cache holds one cell, so a read missed it at every transition and `cache_fill` searched the whole track with `std::upper_bound`. It now first checks the cell after the cached one, accepting it only when its position is at most the wanted position and the next cell's is above it, which is exactly the index the search returns; otherwise it searches. `find_position` and everything after are unchanged. Every frame unchanged (11 game runs), saved states round-trip; RG DS: Alien Syndrome's boot (a disk read throughout) 64.62 -> 67.56 frames a second, gameplay unchanged (Kairo68#5).
- `x68k-line-scroll` (`src/mame/sharp/x68k_crtc.h`, `x68k_crtc.cpp`, `x68k.h`, `x68k_v.cpp`): a write to a CRTC scroll register (R10 to R19) no longer draws the lines the beam has passed (`flush_partial`). It records the registers for those lines and leaves them waiting; `screen_update` draws each line with its own registers (text layer and graphics pages), and in the double-scanned graphics mode, where two screen lines share a graphics row, draws each line's row just before mixing the line, as a call for that line alone did. Every other picture change still draws first and clears the records, the frame's end draws them, a save draws waiting lines first, and nothing is recorded in the special priority mode (the driver's `set_scroll_can_wait`), whose mix reads graphics rows by another divisor. First Blow rewrites the graphics scroll about 96 times a frame per page: 265 `screen_update` calls a frame become 1. The same change makes the drawing's per-pixel work shorter, storing the same values: `draw_sprites` skips sprites whose rows lie outside the lines being drawn before `prio_transpen` clips them; the 16-colour page without blending or the special priority draws in runs that do not wrap GVRAM's row; the layer under BG takes its rows and pens once a line; `decode_text_line` decodes a byte of each plane at a time through a table; the mix runs as a function with the layers' priority levels and the blend mode as template constants. Every frame unchanged (12 verification runs and 12 more games with their second disks), saved states round-trip (Kairo68#29).
- `m68000-ftu-inline` (`src/devices/cpu/m68000/m68000.h`, `m68000.cpp`): `set_ftu_const`, which the generated instruction handlers call once an instruction, is defined inline in the header instead of out of line; the same code (Kairo68#29).
- `x68k-under-row` (`src/mame/sharp/x68k.h`, `x68k_v.cpp`): `screen_update` drew the BG layer under everything into the sprite bitmap and then wrote its pens into the screen bitmap (or filled it with pen 0) for the mix to read back. The layer is drawn into its own bitmap, `m_underbitmap`, and the mix starts each pixel from its pen there, or from pen 0 without it, so a frame no longer writes and rereads the whole screen bitmap before mixing. Every frame unchanged (the 12 verification runs) (Kairo68#29).
- `perf-screen-stages` (`src/mame/sharp/x68k_v.cpp`): a measurement build (`KAIRO68_PERF`) also times `screen_update`'s stages: the layer under BG, the graphics pages, BG and sprites, and the mix.
- `x68k-gvram-1024` (`src/mame/sharp/x68k_crtc.h`, `x68k_crtc.cpp`, `x68k_v.cpp`): in the 1024x1024 16-colour mode the X68000 shows the four graphics pages as the quadrants of one picture, and the CPU addresses G-VRAM as that picture (word y * 1024 + x). MAME read and wrote the words as if they were the 512x512 mode's, and drew the picture from them the same way, so Carat's title and game screens were scrambled stripes. `gvram_r`/`gvram_w` reach a word's quadrant page (`gvram_1024_page`, `gvram_1024_word`), and the 1024x1024 renderer reads each line from the pages of its quadrants, a run of pixels at a time (Kairo68#31).
- `x68k-crtc-unseen-registers` (`src/mame/sharp/x68k_crtc.cpp`): a write to R9 (the raster interrupt line) or R21 to R23 (text access masks, raster copy and clear setup) no longer draws the lines the beam has passed: the hardware reads them only when the CPU writes VRAM or starts an operation, which draw those lines first themselves. Carat's raster interrupt rewrote them on every line, so each line was drawn on its own, 464 `screen_update` calls a frame (Kairo68#30).
- `x68k-unchanged-frame` (`src/mame/sharp/x68k_crtc.h`, `x68k_crtc.cpp`, `x68k.h`, `x68k_v.cpp`): the CRTC counts the changes to anything the picture shows (`flush_partial` and `record_scroll` count one each, as does a load) and notes the count when a frame begins. When a whole frame passes without one after a frame drawn whole without one, `screen_update` reports the screen unchanged (`UPDATE_HAS_NOT_CHANGED`) and the screen keeps the picture it already holds; an interlaced picture, whose fields alternate by themselves, is always drawn. A raster copy (`text_copy` at hsync) onto rows that already hold the same words changes nothing and no longer counts, and the raster interrupt draws the lines above it without counting. Every frame unchanged (the 12 verification runs) (Kairo68#30).
- `x68k-split-check` (`src/mame/sharp/x68k.h`): `x68k_state::kairo68_draw` draws a rectangle of the machine's current state as `screen_update` does, whatever the frame drew before, and leaves the frame's drawing bookkeeping as it was. The split check (`X68kMachine::split_check`, `game_profile --split-check`) draws a frame whole and in two pieces split before each of its lines and compares them (Kairo68#33).
- `x68k-mouse-wrap` (`src/mame/sharp/x68k_mouse.cpp`): the mouse's axes are 12-bit counters, and `read_axis` took their motion as a 16-bit difference, so motion left or up across the counter's wrap point read as a full move the other way and the pointer jumped to the opposite side. The difference is taken as a signed 12-bit number (Kairo68#78).
- `x68k-mouse-pending` (`src/mame/sharp/x68k_mouse.h`): `kairo68_motion_pending` says whether the mouse's axes moved since the guest last polled it. The mouse sends the motion since the last poll, clamped to a packet's -128 to 127, so the core's corner warp gives its next motion only after the guest took the last (Kairo68#78).

The core also builds MAME with `SOUND_DISABLE_THREADING`, as MAME's emscripten build does, and turns off MAME's output audio effects (high-pass filter and EQ by default) through its configuration callbacks; neither changes MAME's sources.

## Generated sources

MAME's build generates some sources from its tree; `tools/generate_mame.py <extracted-mame-root>` writes them to `core/generated/` from the same pinned archive: `version.cpp`, `drivlist.cpp` (MAME's `makedep.py driverlist`, filtered to `sharp/x68k.cpp`), the layouts the subset includes (`complay.py`), the `has_*.h` option headers (as `scripts/genie.lua`'s `generate_has_header`), the CPU sources `cpu.lua` builds with Python (`core/generated/emu/cpu/*/*.hxx`), the per-project source lists `sources.cmake`, and the UI fonts `uismall.fh` (from `scripts/font/NotoSans-Bold.bdc`, SIL Open Font License) and `ui/uicmd14.fh` (from `src/frontend/mame/ui/uicmd14.png`).
